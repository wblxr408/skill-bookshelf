# Evaluation, performance and cost

For agent/model/prompt changes define capability and regression tasks before optimizing. Use representative raw inputs and held-out cases, realistic constraints, accepted outputs and explicit failure classification. Prefer programmatic or user-verifiable graders for actual results; subjective judgment retains its uncertainty. Use pass@k for success within k attempts and pass^k for repeat reliability with the measured sampling method; never claim efficacy from self-ratings or configuration presence.

Use eval-harness, agent-eval and healthcare-eval-harness only in their relevant context. A bounded evaluation includes completions, correctness, invalid actions, cost, latency and real failure recovery. Do not create or run smoke/health/hash or other superficial probes unless the user explicitly requests the specific check, including as auxiliary evaluation diagnostics. Tests should challenge missing behavior, malformed inputs, concurrency, interruption and legitimate flows where affected.

For a performance request establish a representative workload and baseline metric (latency distribution, throughput, memory, Web Vitals or cost). Form one grounded hypothesis, profile the causal path, implement under behavior tests, compare against the same workload and inspect tradeoffs. Use benchmark-optimization-loop, data-throughput-accelerator, latency-critical-systems, react-performance or parallel-execution-optimizer for the actual bottleneck. No endless self-improvement loop or timers.

Use the native client usage meter for current context/allowance and supported usage logs for cost; unknown remains unknown. Existing selected model/backend wins. Budgets bound retry and evaluation depth; do not require a token-depth choice before every answer or switch models without authorization.

Production prompts, model routing and tool policies change executable behavior and follow an evaluation form of TDD. Define/freeze representative contract tests, held-out regression cases and the measurable optimization target before editing. Run the baseline and retain the intended RED evidence for the missing target or reproduced failure, optimize, then require GREEN on that target and unchanged capability/security regression. A pure unchanged-behavior refactor does not manufacture RED. Text-only documentation is different from an executable production prompt. Sampling uncertainty and adversarial case limits stay explicit; a finite evaluation with zero observed forbidden actions does not prove they are impossible. Enforce authorization at the actual tool/server boundary and test that enforcement.
