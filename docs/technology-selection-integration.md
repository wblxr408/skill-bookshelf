# 技术栈与依赖选型流程

更新：2026-10-22。

## 使用范围

新项目、迁移或尚未决定的关键语言、运行时、框架、数据库、库选择，先使用 [tech-stack-evaluator](../local-skills/tech-stack-evaluator/SKILL.md)。读取实际需求、已有实现、部署与资源约束后，比较少量可行候选，说明当前来源、推荐理由和代价。用户明确指定、项目已有决定和普通局部改动保持其技术约束。

网站业务按账号、权限、订单、事务、后台和维护需求判断；模型 API 本身不决定语言。AI 训练和数据处理核实其库生态；CLI、文件索引、同步与执行服务按资源、并发、系统交互及原生分发评估 Rust、Go 等方案。一个产品可以分模块采用不同技术，增加语言也需要计算维护和部署成本。

## 已有入口如何衔接

| 入口 | 负责内容 |
| --- | --- |
| OpenSpec explore / propose / update | 在既有规划与设计中完成需要的技术比较，记录证据、选择和取舍。 |
| OpenSpec apply | 复用已接受的设计；存在实质未决选择或新增关键库时补齐相应比较。 |
| dev / research-contracts / search-first | 按决定实施，调查真正需要新增或替换的库，评估复用、扩展、组合与自研。 |
| tech-stack-evaluator | 提供选型方法、证据边界和简短决策模板，按需使用上游参考资料。 |

相关入口的下载包按 distribution/manifest.json 自动包含 tech-stack-evaluator。全量包保留同一主版本；单独安装选型技能也可由描述发现或显式调用。

## 主动路由示例

本机 Codex 和 Claude 的全局指令已增加条件路由。其他使用者可按自己的客户端和授权范围加入以下简短约定：

> 新项目、迁移或实质未定的技术栈/关键依赖，先读取 tech-stack-evaluator，依据业务、现有代码、部署、资源和维护约束比较候选；保留用户已定技术与项目决策。OpenSpec 记录设计决定，dev 负责实施和库调研。模型 API 不自动确定 Python；基础设施按需要比较 Rust/Go 等方案。官方事实、项目实测和估算分别说明，脚本默认分数不当作实时证据。

## 本次审阅与验收范围

| 场景 | 实际入口约定与审阅结论 |
| --- | --- |
| 带账号、订单和模型 API 的新业务网站 | 从全局路由进入选型，由规划记录业务、部署和维护比较，不能因 API 直接选 Python。 |
| 本地索引 CLI 或长驻执行服务 | 选型包含资源与原生分发条件，按适配情况比较 Rust/Go 及现有生态。 |
| 已确定框架中的局部功能修改 | 保留既有技术，只有新增关键依赖触发对应范围的库调查。 |
| 某库缺少当前维护数据 | 明确资料缺口，不采用脚本默认分数伪造实时结论。 |

以上是对实际技能入口、路由、引用和职责的一致性审阅，并非未来模型执行可靠性或技术性能的实测。书橱新增条目的线上搜索、详情、下载和隔离安装结果由本次发布记录另行记录；既有功能未运行回归测试。

## 多维选型要求 · 2026-10-22 补充

每次实质选型读取 [evaluation-rubric.md](../local-skills/tech-stack-evaluator/references/evaluation-rubric.md)，覆盖功能契合、开发速度、运行速度、资源性能、安全、开源生态、可复用性、库质量、有效库供给、可靠性、维护、部署兼容、总成本及迁移退出。简短决定可以合并表格行，不适用或未知需说明，不能静默省略。

先筛项目硬约束，再按业务优先级比较有依据的候选；不固定万能权重，分清速度与资源性能。库的数量按必要能力对应的实际合格候选判断，质量按具体包、兼容、维护、安全、文档和集成证据判断。上游比较器的缺失默认分与基于分差的置信度不作为决策依据。给出关键条件改变时结论是否改变及复评条件。

本次为实际文档与输出契约审阅及分发更新；不宣称已经验证未来模型每次执行或实际项目性能，不自动新增基准、回归或安全扫描。
