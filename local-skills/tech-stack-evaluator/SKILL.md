# Technology Stack Evaluator

先确定项目和实际决策，再选择技术。复用已知需求、代码、部署环境与有效决定；只询问会改变结论且无法查证的缺失信息。

## 选择范围

- 新项目、迁移或关键技术尚未确定：比较语言/运行时、框架、数据存储、关键库及必要的架构组合。按模块判断，并纳入已有方案复用、扩展或直接采用成熟产品的可行替代；计算多语言和服务拆分的集成代价。
- 用户明确指定技术、项目已有决定：作为约束；普通功能修改直接实施，只比较确实新增或替换的关键依赖。发现约束冲突时说明事实与影响，不能静默改栈。
- 网站和业务应用：按账号、权限、事务、后台、队列、SEO、部署和维护等真实需要比较生态；接入模型 API 本身不是选用 Python 的理由。
- CLI、索引、执行与同步服务等基础设施：按原生分发、启动、内存、并发、跨平台和系统交互要求，考虑 Rust、Go 及已有生态；不能只凭“底层”或“快”确定语言。
- 训练、科研或数据处理：核实实际需要的模型、库和计算环境，生态优势只作用于相应模块。

## 每次选型的比较约定

每次实质选型都读取并使用 [多维选型准则](references/evaluation-rubric.md)，覆盖其中全部维度：功能契合、开发速度、运行速度、资源性能、安全、开源生态、可复用性、库质量、有效库供给、可靠性、维护、部署兼容、总成本及迁移退出。按本项目标明关键项、次要项和不适用项及理由，不能静默省略用户要求的维度。简单库选择可合并表格行、简短表达；调查深度与决策影响相称。

1. 记录真实业务路径、已有实现、团队能力、交付期限、工作负载、部署资源与必要阈值；区分硬约束、偏好和假设。仅对有依据的硬约束判定通过/不通过；关键未知项保留待核实，不能假装通过。
2. 比较少量可行的完整候选组合，先处理功能、安全、许可、预算和部署等硬约束，再按项目优先级取舍。已有方案是可行基线，不设固定候选数或万能权重。
3. 先复用已有实现，再查当前官方文档、包注册表、安全公告、仓库和现有连接器。每个决定性判断给来源/版本/日期，区分官方事实、项目实测、估算、未知；库调研落实到所需能力与具体包。
4. 用 [决策模板](references/decision-template.md) 的内容约定输出比较、推荐、排除理由、接受的代价和复评条件。权重如有使用需解释依据，避免运行速度与资源性能、生态与库供给重复计分。未知数据不填默认中间分，不用分差生成置信概率。
5. 说明改变关键优先级、负载、预算或维护条件时结论是否改变；只有决定性未知项值得进一步验证时，提出或执行当前任务已授权的针对性验证。没有项目实测就保持有条件结论，不冒充已验证性能或未来收益。

## 接入现有流程

OpenSpec 在 explore/propose/update 阶段完成必要比较，将决定、依据与取舍写入已有 design/decision；apply 和 dev 复用该决定，新增关键库时补充对应调查。不要为同一决定创建第二套规格或审批。规划请求保持规划范围；实施请求按已有授权继续。

## 上游资源与适用边界

- 本入口与 [多维选型准则](references/evaluation-rubric.md) 是本地实际方法。上游 [workflows](references/workflows.md)、[metrics](references/metrics.md)、[examples](references/examples.md) 只按需要借鉴，不覆盖本地证据和选型约定。
- 保留的 `scripts/`、`assets/` 和 [原始入口](references/upstream-skill.md) 是辅助资料。先读实际接口和输入再决定是否使用；不强制运行评分、固定五年成本、固定权重或额外测试。
- 上游比较器会为缺失指标填默认值，并从分差生成置信度；metrics 中的 stars/下载量、版本号和企业背书评分均不作为本项目质量、可信概率或安全结论。单一候选不代表 100% 置信；更少 CVE、更新更频繁、依赖更少也不能单独证明更好。
