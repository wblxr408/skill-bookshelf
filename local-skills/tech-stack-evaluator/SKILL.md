# Technology Stack Evaluator

先确定项目和实际决策，再选择技术。复用已知需求、现有代码、部署环境与有效决策；只询问会改变结论且无法查证的缺失信息。

## 选择范围

- 新项目、迁移或关键技术尚未确定：比较语言/运行时、主要框架、数据存储和关键依赖。分模块判断，避免把一个模块的需求扩展为整个产品的技术栈。
- 已有技术栈或用户明确指定方案：将其作为约束；普通功能修改直接实施，只比较确实新增或替换的关键依赖。
- 网站和业务应用：考虑账号、权限、事务、后台、队列、SEO、部署和维护。按适配情况比较 PHP、TypeScript、Java、Python、Go 等生态；接入模型 API 本身不是选用 Python 的理由。
- CLI、文件索引、执行器、同步服务等基础设施：考虑原生分发、启动、内存、并发、跨平台、系统调用和长期维护，按适配情况纳入 Rust、Go 及已有生态。不能仅凭“底层”或“性能”直接确定语言。
- 训练、科研或数据处理：核实实际需要的模型、库及计算环境；Python 的生态优势只作用于相应模块。

## 比较与证据

1. 记录业务流程、已有实现/技能、维护者能力、资源预算、交付时间、部署平台与必要约束；已知信息不重复访谈。
2. 对尚未决定且影响结果的选择，提出少量可行候选，按功能契合、集成成本、维护、安全、许可、资源、部署和迁移代价比较。候选数量随决策规模调整，明确指定的方案不强行重新比赛。
3. 先复用项目已有方案，再检索包注册表、官方文档、官方仓库与现有连接器。关键库核实当前版本兼容性、许可证、维护状态、依赖负担和真实缺失能力。标明来源、日期、估算及未核实项。
4. 明确推荐、主要取舍、排除其他候选的原因，以及什么事实变化会使结论失效。有必要实测时只提出或执行已授权且针对当前决策的验证；不编造性能、价格或漏洞结论。

输出可使用 [决策模板](references/decision-template.md)，简单依赖选择用简短比较即可。没有可用的当前数据时给出有条件结论，不以热度或虚构数字补齐证据。

## 接入现有流程

OpenSpec 负责需求和设计：在 explore/propose/update 阶段完成必要比较，把选择、来源和取舍写入现有 design/decision 位置。dev 负责实施：复用该决策，新增关键库时按 research-contracts/search-first 补充调查。不要为同一决定额外创建另一套规格或批准流程。规划请求保持规划范围；实施请求在已有授权下继续执行。

## 按需使用上游资源

- 比较、成本或迁移的方法：只读对应的 [workflows](references/workflows.md)、[metrics](references/metrics.md) 或 [examples](references/examples.md) 分支。
- `scripts/` 和 `assets/` 是保留的计算辅助与示例。脚本根据输入、固定规则和默认值计算，不保证实时采集；先审阅实际脚本接口与输入，再决定是否适用。不得把默认评分、置信等级、样例成本或安全判断当成当前事实或项目验证，也不强制采用固定五年成本周期、权重或分数阈值。
- 原始入口见 [upstream-skill.md](references/upstream-skill.md)，作为上游资料；本入口和用户/项目执行约束决定实际流程。
