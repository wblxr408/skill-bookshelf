# 多维技术与库选型准则

每次实质选型覆盖下表全部维度，按任务标出关键/次要/不适用及原因。覆盖不是要求每次都做长报告、跑基准或联网统计整个生态；聚焦会改变决定的证据，低影响项简述，未知项明示。

## 比较对象与项目目标

比较能实现同一业务路径的语言/运行时、框架、必要库、数据库和部署组合；选择单个库时保持外围技术一致。先写目标负载、数据规模、资源限制、交付期限、团队能力和已知瓶颈。已有成熟实现、扩展现有方案、托管服务或小范围原生加速均可成为候选；避免只在语言名称间泛比。

硬约束如必需功能、目标平台、数据要求、许可、安全底线、预算和明确的延迟/资源上限先筛选。无法满足者不靠其他维度高分补偿；关键证据未知者标记待核实，并给条件性决定。

## 必须考虑的维度

| 维度 | 本项目需要判断什么 | 有用的依据与误区 |
| --- | --- | --- |
| 功能与业务契合 | 核心流程、数据模型、事务/一致性、平台或领域能力是否支持；需要多少补写 | 真实需求、现有代码、对应版本官方能力；网站按需要看 SEO/可访问性/后台，不能套用无关要求 |
| 开发速度 | 首次交付、后续迭代、学习、集成、调试与构建反馈成本 | 团队熟悉度、可复用模块、脚手架/文档/API 与工具支持；AI 辅助只计入有实际依据的收益，不以代码行数或模型熟悉度代替交付速度 |
| 运行速度 | 用户路径延迟、任务耗时、冷启动与预热后的响应、交互流畅度 | 服务看适用的 p50/p95/p99、CLI 看启动与目标任务、批处理看完成时间；先定位 CPU/I/O/数据库/外部 API 瓶颈，不将微基准推广为整站速度 |
| 资源性能与扩展 | 在指定 CPU/内存/I/O/网络预算下的吞吐、并发、容量、伸缩与饱和行为 | 同等硬件与功能下的资源和负载数据；区分单次快、单位资源效率与负载上限，和运行速度重叠的数据只计一次 |
| 安全与供应链 | 项目需要的身份/权限、输入与数据保护、安全默认值、依赖风险和可维护的补丁路径 | 当前目标版本公告及适用性、官方生命周期、安全策略与修复响应；内存安全只是部分风险，少 CVE、语言类型或一个扫描分数均不能证明系统安全 |
| 开源生态健康 | 相关领域的维护连续性、治理、文档、支持寿命、贡献与替代选择 | 维护者集中度、发布/兼容政策、真实问题处理、成熟度；stars/下载量/大厂背书仅作背景，稳定项目低频发布不自动淘汰 |
| 可复用性 | 已有代码、技能、组件、契约、数据与团队知识能复用多少；结果能否跨模块/项目复用 | 实际复用清单、适配边界、跨语言/服务通信与集成维护成本；不能为了抽象复用制造额外架构 |
| 库的质量 | 将要采用的核心库是否正确、成熟、好用、可维护且兼容 | API/类型/文档、相关场景的测试与缺陷记录、性能、许可、依赖树、维护响应和迁移说明；不直接复刻某库覆盖率或版本号为质量分 |
| 有效库供给与数量 | 每项必要能力有无适配目标平台和版本、可维护且许可允许的库，以及替代余地 | 建立“能力→主选库/备选→兼容状态/缺口”的覆盖表；只记录实际核实的合格候选，不以包注册表总量、同名包装/废弃包数量代替项目可用库数量 |
| 可靠性与数据正确性 | 故障恢复、隔离、重试/幂等、备份、事务、升级与负载失败的影响 | 按业务需要查实际机制与运维能力；不强迫每个项目增加分布式系统设施 |
| 维护与可观测性 | 类型和契约、复杂度、调试/日志/指标、升级成本、交接和人员能力 | 现有团队与工具、长期支持/破坏性变更政策、可诊断性；同时看修复与日常迭代成本 |
| 部署与兼容 | 当前宿主、操作系统、架构、原生分发/容器/无服务器限制、离线要求、交付链路 | 官方平台支持、实际部署配置、构建产物与系统依赖；只比较本次相关平台，不能默认可迁移 |
| 总成本 | 开发、学习、集成、机器/网络/存储、托管/许可、维护和迁移成本 | 匹配项目预期寿命与增长场景，价格注明日期与条件，工时给区间及假设；不固定五年或编造精确省钱比例 |
| 可移植性与退出 | 厂商/框架绑定、数据导出、协议兼容、替换核心库与未来迁移的代价 | 接口/数据格式、实际耦合与退出路径；多语言或托管服务的收益需与集成和迁移代价一起看 |

按项目补充没有被表格覆盖的决定性条件，例如实时期限、能耗、弱网、移动端体积、数据位置或专用硬件；说明其业务理由，不默认添加合规或全面审计流程。

## 库调查与证据

对需要引入的关键库列出：所解决能力、准确包名与当前版本/支持线、官方来源、平台/运行时兼容、维护与安全情况、许可、集成成本和可替代性。实际差异由需要使用的 API、限制和代码证据支持；没有调查全生态就不宣称某语言“缺库”。已有库满足需要时比较新增依赖是否值得。

每个决定性判断标为官方资料、项目实测、估算或未知，并附适用版本、日期或实验条件。官方文档证明能力和约束，不等同于本项目端到端性能。上游基准属于外部证据，说明工作负载与当前任务的差别；没有证据不虚填 50 分，不把推荐表达成统计置信概率。

## 取舍方法

- 先筛硬约束，再明确本次最重要的业务目标。一般采用有依据的定性比较；用户或项目需要量化时才给可解释的尺度、来源和权重，避免重叠指标重复计分。
- 删除明显被其他候选全面覆盖而没有优势的方案；对剩余候选说明为何某项收益值得其代价。无法区分时给有条件推荐或保留备选，不制造精确排名。
- 做简短条件变化分析：期限、流量、资源、维护者能力、库支持线等关键条件改变时，推荐是否反转；给复评触发条件，而非预言未来技术趋势。
- 决定性未知项需要验证时，限定真实业务路径和成功阈值。性能比较控制功能/正确性、版本配置、硬件、数据、并发与冷/热状态，同时报告错误率和资源消耗；开发速度验证看可工作的业务片段及实际投入。是否执行按当前授权及项目验证约束决定，不默认跑基准、回归、冒烟或扫描。

## 方法资料与边界

以下是方法依据，查阅于 2026-10-22；实际选型仍须检索目标技术/库的当前官方证据。

- [Google SRE：Monitoring Distributed Systems](https://sre.google/sre-book/monitoring-distributed-systems/)：延迟、流量、错误、饱和度和分位数为服务表现提供不同视角；本表据此将响应速度与资源/容量分开观察。
- [OWASP ASVS](https://owasp.org/www-project-application-security-verification-standard/)：提供应用技术安全控制与开发需求参考；只引用适用控制，不代表选了某框架便符合标准。
- [OpenSSF Scorecard](https://github.com/ossf/scorecard)：自动启发式检查可提供开源项目安全实践信号；评分只作证据之一，不作保证安全或替代项目风险判断。
