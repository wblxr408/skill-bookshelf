# 按需深入的选型参考

入口已给出全部筛查维度和调查边界。本文件用于解决具体疑问，读取相应节即可，不要求整篇加载或逐项联网。已读且适用的证据直接复用；调查与输出按入口的项目边界、证据缺口与收敛条件调整。

## 交付与长期使用

| 维度 | 本项目需要判断什么 | 有用的依据与误区 |
| --- | --- | --- |
| 功能与业务契合 | 核心流程、数据模型、事务/一致性、平台或领域能力是否支持；需要多少补写 | 真实需求、现有代码、对应版本官方能力；网站按需要看 SEO/可访问性/后台，不能套用无关要求 |
| 开发速度 | 首次交付、后续迭代、学习、集成、调试与构建反馈成本 | 团队熟悉度、可复用模块、脚手架/文档/API 与工具支持；AI 辅助只计入有实际依据的收益，不以代码行数或模型熟悉度代替交付速度 |
| 可复用性 | 已有代码、技能、组件、契约、数据与团队知识能复用多少；结果能否跨模块/项目复用 | 实际复用清单、适配边界、跨语言/服务通信与集成维护成本；不能为了抽象复用制造额外架构 |
| 可靠性与数据正确性 | 故障恢复、隔离、重试/幂等、备份、事务、升级与负载失败的影响 | 按业务需要查实际机制与运维能力；不强迫每个项目增加分布式系统设施 |
| 维护与可观测性 | 类型和契约、复杂度、调试/日志/指标、升级成本、交接和人员能力 | 现有团队与工具、长期支持/破坏性变更政策、可诊断性；同时看修复与日常迭代成本 |
| 部署与兼容 | 当前宿主、操作系统、架构、原生分发/容器/无服务器限制、离线要求、交付链路 | 官方平台支持、实际部署配置、构建产物与系统依赖；只比较本次相关平台，不能默认可迁移 |
| 总成本 | 开发、学习、集成、机器/网络/存储、托管/许可、维护和迁移成本 | 匹配项目预期寿命与增长场景，价格注明日期与条件，工时给区间及假设；不固定五年或编造精确省钱比例 |
| 可移植性与退出 | 厂商/框架绑定、数据导出、协议兼容、替换核心库与未来迁移的代价 | 接口/数据格式、实际耦合与退出路径；多语言或托管服务的收益需与集成和迁移代价一起看 |

## 运行速度与资源

| 维度 | 本项目需要判断什么 | 有用的依据与误区 |
| --- | --- | --- |
| 运行速度 | 用户路径延迟、任务耗时、冷启动与预热后的响应、交互流畅度 | 服务看适用的 p50/p95/p99、CLI 看启动与目标任务、批处理看完成时间；先定位 CPU/I/O/数据库/外部 API 瓶颈，不将微基准推广为整站速度 |
| 资源性能与扩展 | 在指定 CPU/内存/I/O/网络预算下的吞吐、并发、容量、伸缩与饱和行为 | 同等硬件与功能下的资源和负载数据；区分单次快、单位资源效率与负载上限，和运行速度重叠的数据只计一次 |

需要性能证据时先定位 CPU/I/O/数据库/外部服务瓶颈。外部基准注明与项目的差异；针对性实测如已获授权，控制功能正确性、版本、配置、硬件、数据、并发和冷/热状态，同时看错误与资源。没有实测就保留条件，不为补齐报告自动运行基准。

## 生态、关键库与安全

| 维度 | 本项目需要判断什么 | 有用的依据与误区 |
| --- | --- | --- |
| 安全与供应链 | 项目需要的身份/权限、输入与数据保护、安全默认值、依赖风险和可维护的补丁路径 | 当前目标版本公告及适用性、官方生命周期、安全策略与修复响应；内存安全只是部分风险，少 CVE、语言类型或一个扫描分数均不能证明系统安全 |
| 开源生态健康 | 相关领域的维护连续性、治理、文档、支持寿命、贡献与替代选择 | 维护者集中度、发布/兼容政策、真实问题处理、成熟度；stars/下载量/大厂背书仅作背景，稳定项目低频发布不自动淘汰 |
| 库的质量 | 将要采用的核心库是否正确、成熟、好用、可维护且兼容 | API/类型/文档、相关场景的测试与缺陷记录、性能、许可、依赖树、维护响应和迁移说明；不直接复刻某库覆盖率或版本号为质量分 |
| 有效库供给与数量 | 每项必要能力有无适配目标平台和版本、可维护且许可允许的库，以及替代余地 | 建立“能力→主选库/备选→兼容状态/缺口”的覆盖表；只记录实际核实的合格候选，不以包注册表总量、同名包装/废弃包数量代替项目可用库数量 |

只调查当前必要能力对应的核心包：准确名称、版本/支持线、官方来源、兼容、维护、安全、许可、集成代价和合格备选；缺库结论限定于实际查过的能力与范围。已有库满足要求时先考虑复用。少 CVE、单项安全评分、stars 或下载量不能独立证明质量；不同候选的生态规模不作无依据的完整计数。

## 需要进一步取舍时

调查深度与项目复杂度匹配：单个库优先复用既有生态，核实决定性的适配与维护缺口；多模块新项目或高代价迁移按模块比较并核实边界、数据与集成影响，避免枚举全部技术组合。可信证据冲突、关键性能/安全未知值得继续追查对应问题；候选、来源与轮数随这些需要调整，不以完成固定次数结束，也不为追求全覆盖持续追加范围。每批取证说明得到什么新信息、还有什么可能改变决定；无信息增益的方向及时停止。

优先使用有依据的定性比较。只有量化有助于当前决定时才解释尺度、权重和来源，避免速度与资源性能、生态与库供给重复计分。硬约束不能由其他优势补偿，关键未知不得假装通过；去掉明显被其他候选覆盖而无优势的方案，无法区分时给条件性推荐或备选。

说明期限、负载、资源、预算、维护能力或关键库支持线变化是否会改变推荐。其他领域约束只在项目确实需要时补充，例如实时期限、能耗、移动端体积或专用硬件；不据此无限扩展调查。

## 方法来源

2026-10-22 已查阅以下方法资料，实际选型按需查目标技术的当前证据，无需为同一方法重复检索：
- [Google SRE](https://sre.google/sre-book/monitoring-distributed-systems/)：延迟、流量、错误与饱和度提供不同视角。
- [OWASP ASVS](https://owasp.org/www-project-application-security-verification-standard/)：适用的应用安全控制需求参考。
- [OpenSSF Scorecard](https://github.com/ossf/scorecard)：开源安全实践信号及其局限，不提供安全保证。
