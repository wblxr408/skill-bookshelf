# 多 Agent 安全基线

用户要求后续多 Agent 开发显式调用已沉淀的 A2ABreak 方案。相关设计、实现或评审开始时，说明正在应用 A2ABreak 安全基线及本次适用编号。本技能不授权启动子 Agent。

## 检索与适用性

读取 Basic Memory 项目 `main` 的 `main/engineering/security/a2abreak/a2-abreak-多-agent-安全基线与-11-项方案索引`。连接不可用时按 engineering-memory 的回退规则读取已确认本地文件 `~/basic-memory/engineering/security/a2abreak/A2ABreak 多Agent安全基线与11项方案索引.md`。

初次架构设计评估 A2AB-01 至 A2AB-11：技能准入、Card 密钥信任、上下文隔离、SSE 撤权、产物完整性、并发控制、Webhook、授权范围、多跳身份、环路预算、中断租约。增量开发复用已读且仍有效的评估，只重新检查变动涉及的方案。没有对应功能时说明不适用的具体原因。

读取适用方案完整条目，不能仅凭索引标题实施。索引和方案版本以实际读取结果为准；初始基线为 v1.0。普通多 Agent 系统按实际信任边界借鉴，不能宣称全部受 A2A 漏洞影响。

## 显式应用

在设计或开发交付中标注：`A2AB-XX / 方案标题 / 基线版本 / 方案章节`，附知识库引用，并说明本次执行组件、实现控制点、验收办法与实际结果。示例：`A2AB-03 / 上下文归属与跨租户隔离 / v1.0 / 工程解决方案`；实际章节名以读到的条目为准。

授权、隔离、预算和状态一致性由服务端可信组件执行；不要把提示词当作权限控制。新增字段或协议行为需要明确扩展协商、兼容策略和不支持时的安全处理，不能称为 A2A 核心规范已有字段。

方案的验收用例是实施时的验证要求；选择能覆盖变更的攻击路径及合法路径。没有执行的检查写待验证，不能以来源核对或形式化抽象模型替代部署验证。

## 证据与维护

区分论文/仓库中的发现、当前规范要求和本地提出的防护方案。论文针对的版本与部署版本不同，先核对相关规范；保留索引中的版本差异，尤其是任务内授权语义和中断状态转换。不要自行编造 CVE、官方修复状态或完整安全保证。

按 engineering-memory 技能更新实际项目验证证据、环境、版本、失败和替代方案。只在已有实测证据覆盖的范围内提升验证状态。任何例外记录具体理由和补偿措施；不机械复制 11 项到无关修改。
