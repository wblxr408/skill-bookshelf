# Evaluation, performance and cost

For agent/model/prompt changes define the current capability/optimization target before editing. Regression evaluations, including capability/security regression, are prohibited unless the user explicitly requests the specific checks and scope. Use representative raw inputs for the current target, realistic constraints, accepted outputs and explicit failure classification. Prefer programmatic or user-verifiable graders for actual results; subjective judgment retains its uncertainty. Use pass@k for success within k attempts and pass^k for repeat reliability with the measured sampling method; never claim efficacy from self-ratings or configuration presence.

Use eval-harness, agent-eval and healthcare-eval-harness only in their relevant context. A bounded evaluation includes completions, correctness, invalid actions, cost, latency and real failure recovery. Do not create or run smoke/health/hash or other superficial probes unless the user explicitly requests the specific check, including as auxiliary evaluation diagnostics. Tests should challenge missing behavior, malformed inputs, concurrency, interruption and legitimate flows where affected.

For a performance request establish a representative workload and baseline metric (latency distribution, throughput, memory, Web Vitals or cost). Form one grounded hypothesis, profile the causal path, implement under behavior tests, compare against the same workload and inspect tradeoffs. Use benchmark-optimization-loop, data-throughput-accelerator, latency-critical-systems, react-performance or parallel-execution-optimizer for the actual bottleneck. No endless self-improvement loop or timers.

Use the native client usage meter for current context/allowance and supported usage logs for cost; unknown remains unknown. Existing selected model/backend wins. Budgets bound retry and evaluation depth; do not require a token-depth choice before every answer or switch models without authorization.

Production prompts, model routing and tool policies change executable behavior and follow focused evaluation TDD. Freeze the current change's minimal contract and measurable target, observe its baseline failure, then require GREEN on that same target. Do not create or run held-out capability/security regression cases or existing evaluation suites without an explicit user request for those checks. A pure unchanged-behavior refactor does not manufacture RED or automatically trigger regression. Text-only documentation uses actual consistency review. Sampling uncertainty and adversarial case limits stay explicit; finite evaluations do not prove forbidden actions impossible. Enforce authorization at the tool/server boundary and verify newly changed enforcement within the current target.
